## 2. Why Data Flow Analysis Was Added

Structural analysis alone cannot determine how values move through a program.

For example:

    user_input = request_input()
    query = user_input.strip()
    execute(query)

Metrics can identify:

- function complexity
- number of calls
- branches
- loops

The Call Graph can identify:

    test()
      ↓
    request_input()
      ↓
    execute()

The CFG can identify possible execution paths.

However, Code Guardian AI also needs to understand:

    request_input()
          ↓
      user_input
          ↓
      user_input.strip()
          ↓
         query
          ↓
       execute(query)

This is the purpose of Data Flow and Taint Analysis.

## 3. Data Flow Milestone 1

The initial Data Flow layer was implemented around definitions and uses.

The main concepts are:

- Definition.
- Variable use.
- Defined-variable set.
- Used-variable set.

A definition represents a point where a variable receives a value.

A use represents a point where a variable's value is read or consumed.

Example:

    x = 10
    y = x + 5

The analysis identifies:

    Definitions:
        x
        y

    Uses:
        x

This provides the foundation for more advanced data-flow analyses.

## 4. Reaching Definitions

A Reaching Definitions analysis was implemented as a forward MAY data-flow analysis.

The standard equations are:

    IN[n] = union(OUT[p])

    OUT[n] = GEN[n] ∪ (IN[n] - KILL[n])

where:

- `IN[n]` represents definitions reaching a node.
- `OUT[n]` represents definitions leaving a node.
- `GEN[n]` represents definitions generated by the node.
- `KILL[n]` represents definitions invalidated by the node.

The implementation maintains definition references and the corresponding `gen`, `kill`, `in`, and `out` sets.

This provides the foundation for connecting variable uses to possible definitions.

---

## 5. Def-Use Chains

Def-Use Chain analysis was implemented on top of reaching definitions.

A Def-Use Chain connects:

    Definition
        ↓
       Use

For example:

    x = request_input()
    execute(x)

The system can represent:

    x definition
        ↓
    x use

The Def-Use layer also maintains stable IDs for relevant uses so that later security analysis can reference the same data-flow evidence.

Generic call names such as `print` are not incorrectly treated as local variable definitions.

---

## 6. Use-Before-Definition Analysis

Use-Before-Definition (UBD) analysis was implemented to detect cases where a variable is used before it is definitely defined.

Example:

    print(x)
    x = 10

This should produce a finding for `x`.

A critical semantic issue was identified during development.

Reaching Definitions is a MAY analysis. Therefore, at a branch join, a definition that reaches from only one predecessor may still appear in the reaching set.

For UBD, that is not sufficient.

UBD therefore uses MUST-style reasoning so that a variable is considered definitely defined only when its definition is guaranteed across the relevant control-flow paths.

This correctly handles branch and loop cases.

Final UBD test suite:

    13 passed

---

## 7. Dead Definitions

Dead Definition analysis was implemented using the relationship between definitions and uses.

A definition is considered dead when its value is never subsequently used.

Example:

    x = calculate()
    y = 10
    return y

The definition of `x` can be identified as dead because the assigned value is never used.

The analysis is based on Def-Use information instead of treating every unused parameter as a dead store.

Final Dead Definition test suite:

    10 passed

## 8. Taint Analysis

A Taint Analysis subsystem was implemented to track potentially untrusted values through a function.

The main concepts are:

- Taint sources.
- Tainted variables.
- Taint propagation.
- Taint sinks.
- Taint flow findings.

The basic security flow is:

    Source
      ↓
    Tainted Value
      ↓
    Propagation
      ↓
    Sink
      ↓
    Security Finding

Example:

    user_input = request_input()
    execute(user_input)

The analyzer detects that data from a source reaches a dangerous sink.

---

## 9. Taint Sources

Default source names include:

    input
    request_input
    get_user_input

The system also supports additional source names supplied by the caller.

A source represents a location where externally controlled or potentially untrusted data enters the program.

Example:

    user_input = request_input()

The resulting value is marked as tainted.

---

## 10. Taint Sinks

Default sink names include:

    execute
    execute_query
    run_command

A sink represents an operation where tainted data may cause a security problem.

Example:

    user_input = request_input()
    execute(user_input)

The analyzer records the sink and checks whether tainted data reaches it.

## 11. Taint Propagation

Taint propagation was extended beyond direct variable assignments.

Basic propagation:

    user_input = request_input()
    query = user_input

Results in:

    request_input()
          ↓
      user_input
          ↓
        query

The tainted state follows the value as it moves through assignments and expressions.

---

## 12. Method-Call Propagation

A subtle taint propagation issue was identified and fixed for method calls.

Example:

    user_input = request_input()
    query = user_input.strip()
    execute(query)

In Python AST, the tainted value in:

    user_input.strip()

is stored as the receiver of the `Attribute` node rather than as a normal function argument.

The implementation was therefore extended to propagate taint through method receivers.

The resulting flow is:

    request_input()
          ↓
      user_input
          ↓
    user_input.strip()
          ↓
        query
          ↓
    execute(query)

A dedicated regression test was added and passed.

## 13. Sanitizers

Sanitizer support was added as the next Taint Analysis milestone.

Default sanitizer names include:

    sanitize
    escape
    escape_sql
    html_escape
    sanitize_sql
    sanitize_html
    quote

A sanitizer removes the tainted state from the resulting value.

Example:

    user_input = request_input()
    safe_value = sanitize(user_input)
    execute(safe_value)

The sanitizer prevents the taint flow from reaching the sink.

The system also supports custom sanitizer names.

This makes the analyzer configurable for project-specific security utilities.

---

## 14. Sanitizer Evidence

Sanitizer calls are explicitly recorded in the taint analysis result.

This allows future reporting layers to explain not only:

    source → sink

but also:

    source → sanitizer → safe value

This distinction is important for reducing false positives and making security findings explainable.

## 15. Vulnerability Rules

A vulnerability-rule layer was introduced above raw taint flows.

Instead of reporting only:

    tainted value reaches sink

the system can classify the flow into a security category.

The current rule engine contains rules for:

- SQL Injection.
- Command Injection.
- Path Traversal.
- Cross-Site Scripting (XSS).

Each rule contains:

    rule_id
    name
    severity
    description
    source_names
    sink_names

---

## 16. SQL Injection Rule

The SQL Injection rule matches flows where untrusted input reaches SQL-related sinks.

Typical sinks include:

    execute
    execute_query
    execute_sql
    raw_query
    query

The default severity is:

    CRITICAL

Example:

    user_input = request_input()
    execute_query(user_input)

The resulting flow can be classified as SQL Injection.

---

## 17. Command Injection Rule

The Command Injection rule identifies tainted input reaching command-execution operations.

Typical sinks include:

    run_command
    execute_command
    system
    popen
    run

The default severity is:

    CRITICAL

Example:

    command = request_input()
    run_command(command)

This can be classified as Command Injection.

Typical sinks include:

## 19. XSS Rule

The XSS rule identifies tainted input reaching HTML or response rendering operations.

Typical sinks include:

## 21. Interprocedural Taint Analysis

The next milestone extended taint analysis across function boundaries.

Example:

    def get_data():
        return request_input()

    def execute_data(value):
        execute(value)

    def main():
        data = get_data()
        execute_data(data)

The desired flow is:

    request_input()
          ↓
       get_data()
          ↓
         data
          ↓
    execute_data()
          ↓
       execute()
          ↓
    vulnerability

This allows Code Guardian AI to detect security flows that do not occur entirely inside one function.

## 23. Interprocedural Sanitization

Sanitization was also considered across function boundaries.

Example:

    def sanitize_input(value):
        return sanitize(value)

    def main():
        value = request_input()
        safe = sanitize_input(value)
        execute(safe)

The intended security reasoning is:

    source
      ↓
    tainted value
      ↓
    sanitizer function
      ↓
    safe value
      ↓
    sink

This prevents the analyzer from treating every source-to-sink path as automatically vulnerable.

## 24. Clean Interprocedural Values

The interprocedural analysis was tested against clean values as well.

Example:

    def get_constant():
        return "fixed"

    def main():
        value = get_constant()
        execute(value)

Because the value does not originate from a configured taint source, the analyzer should not report a taint vulnerability.

This is important for controlling false positives.
